## 1. 我们适配的平台

本 fork 将原先面向 **Radxa Zero 3W / RK3566 / aarch64** 的 SDK，扩展到
**SpaceMIT K1 / RISC-V 64 位**。当前验证环境如下：

| 项目 | 已验证环境 |
| --- | --- |
| 开发板 | 原 K1 4 GB；新增 MUSE-Pi-Pro / K1 8 GB（IMX219 路径） |
| 操作系统 | 原板 Bianbu 2.1.1；MUSE-Pi-Pro Bianbu 2.3.5 |
| Rust 目标 | `riscv64gc-unknown-linux-gnu`；系统 `uname -m` 为 `riscv64` |
| Rust 工具链 | 独立安装 1.89.0，保留 apt 的 1.75.0，不替换系统编译器 |
| 推理运行时 | 原生 `spacemit-onnxruntime` 2.0.6-bpo1+1：ORT 1.24.2+spacemit.a1、SpaceMIT EP 2.0.6 |
| 多媒体 | GStreamer 1.24.2；可选私有 SpaceMIT MPP / V2D 桥接及 `opencv-spacemit` 4.14.0-1bb3 |
| 已测外设 | 原板 DECXIN USB 摄像头（`1bcf:2d50`，双目拼接帧中选一眼）、ES8326 音频；MUSE-Pi-Pro 的 CSI3 IMX219 |

这是针对上述 K1 软件栈和外设的适配，不表示任意 RISC-V 板卡、摄像头或系统镜像均已通过验证。
Mac 上的构建和测试用于开发检查，不能替代 K1 原生执行及外设验收。

## 2. 已经适配了多少功能

沿用项目最初的 **10 类功能模块**，当前状态为：

- **4 类已验证**：完成当前限定范围的软件或板级功能验收。
- **3 类部分完成**：已有可用子路径，但原模块的其他子路径尚未完成。
- **3 类待联调或集成**：尚未通过实物或端到端验收；不表示这些模块完全没有可复用代码。

因此后续还将继续推进 **6 类模块的剩余工作（3 类部分完成 + 3 类待联调）**，并对整机做综合验收。
各模块工作量不同，不能将上述数量解释为“完成了 40% 工时”或用新增代码行数计算适配率。

| 编号 | 功能模块 | 当前状态 | 已完成内容与剩余边界 |
| --- | --- | --- | --- |
| 1 | Rust / RISC-V 运行基础 | 已验证 | 独立 Rust 1.89、SDK 全量原生编译、程序加载和回归工具已可用；不是全套外设验收。 |
| 2 | 强化学习策略与控制软件 | 已验证 | 9 个官方 ONNX 策略在 K1 运行；fake IO 下验证约 50 Hz 控制循环。真实舵机闭环归入第 3 项。 |
| 3 | DXL / 舵机 / IMU | 待联调 | 控制核心和协议代码保留；还需接 HAT，验证 K1 UART 半双工、1 Mbps、15 个舵机、IMU 及真实控制闭环。 |
| 4 | 视觉检测 | 已验证 | Rust ORT + SpaceMIT EP 已接入 SDK、配置和检测工具；实时单眼检测满足当前 2 Hz 目标。带标注精度和整机并发验收仍需补充。 |

| 6 | H.264 / RTSP / WebRTC 图传 | 部分完成 | SDK 可选 `camera-rtsp` 已接入 IMX219→NV12 DMA-BUF→K1 H.264 硬编→RTSP/TCP，并由电脑播放器解码；检测框、WebRTC、浏览器控制和整机并发尚未完成。 |

| 9 | 蓝牙 / 手柄 | 待联调 | 相关程序可原生构建；控制器、配对、输入、断连恢复及实际控制链路仍需验收。 |

**USB 相机当前需求是单眼使用，已经完成该范围的适配。** 摄像头物理上有两眼，不代表要同时推理两眼；
`camera.view` 选择左眼或右眼即可。第 5 项仍标为“部分完成”是因为 IMX219 还需图像质量和长稳验收，
不是因为 USB 单眼还欠一次双眼验收。双眼同时推理、双目深度和标定不属于本阶段交付要求。

## 3. 已完成能力的实测依据

### 原生构建、策略与控制软件

- SDK 已在 K1 使用 Rust 1.89 全量原生构建。开发安装复验中，12 个已安装的守护程序/诊断工具通过
  `--help` 加载检查，复制后的二进制与构建产物逐字节一致。加载成功不代表对应硬件功能已经完成。
- 9 个策略分别加载、各使用 1 个 ORT intra-op 线程，无绑核、无其他业务并发；每模型预热 20 次、测量
  200 次，平均推理耗时约 **0.88–0.94 ms**。该数值不含模型加载和总线操作，也不是整机控制循环耗时。
- K1 上使用 fake IO 的控制测试持续约 30 秒，完成 1,500 个周期，约 **49.986 Hz，零 missed deadline**。
  这是真实 K1 上的模拟硬件 IO 验证，尚不能据此宣称机器人已经能在 K1 上行走。

复现条件和原始记录见 [策略与控制软件验证](spacemit-k1.md#validate-real-policy-inference)。

### USB 单眼与视觉检测

- 摄像头采用 DECXIN 的 MJPEG 4000×1200 原始拼接帧，选取一眼、保持宽高比输出 1280×720。
  在硬限制为 4 个 CPU 的条件下，采集单独测试经 5 次预热、120 帧测量，约 **30.05 fps**；
  同条件软件路径约 5.39 fps。它是采集吞吐，不是浏览器图传帧率。
- 浮点 opset 17 鸭子检测模型已通过 SDK 原有前后处理接入原生 ORT / EP。硬 CPU 集合为
  `AllowedCPUs=0-2,4`，EP 的 3 个工作线程在 `0;1;2`，调用线程在 CPU 4；未开启 FP16 epilogue。
  5 次预热、60 次测量，最终构建的实时单眼检测平均 **192.8 ms**、P95 **209.4 ms**，按 2 Hz 消费。
  检测耗时包含前处理、推理和 NMS，不包含摄像头采集/裁剪/缩放。
- 多次硬件路径测量的检测均值在 **187–206 ms** 间变化，不能把最快一次当作保证值。
  测试时未并发运行真实舵机、音频、编码或 WebRTC。
- MPP / V2D 和软件解码/缩放的实际图像输出**不是逐字节一致**；不同 EP 的检测输出也不能由性能测试
  推导为精度等价。加速路径保持显式启用，未默认切换 INT8；带标注的检测精度仍待验收。
- EP 兼容模型 `duck_detect.slim.onnx` 仍是实验产物，**尚未作为 K1 发布资产交付**。
  开发安装不会自动生成它；不能直接使用原始 opset 12 ONNX、RKNN 文件或通用 COCO 模型替代。

配置、模型校验值、重复测量和失败记录分别见 [Rust ORT / EP](k1-duck-ort-ep.md)、
[USB 相机](k1-usb-camera.md) 和 [MPP / V2D / OpenCV 验收](k1-mpp-camera.md)。

### MUSE-Pi-Pro / IMX219

新增 `spacemit_csi` source，通过板上现有 `spacemitsrc` 管理 CSI3 / IMX219 的 ISP/CPP，
再复用 SDK 的 UYVY 取帧与 ORT/EP 检测。没有重编 sensor 驱动、修改设备树或替换原 RKNN/USB 路径。
新板 library 回归 719 项通过，且 IMX219 同进程连续 3 次打开/取帧/关闭通过；
硬限制 4 个 CPU，两轮 720p 采集约 26.7 fps；浮点鸭子模型的前处理＋推理＋NMS 平均
237.6–248.9 ms，P95 247.9–259.2 ms，按 2 Hz 消费；独立 profile 确认执行 SpaceMIT 子图。
测试时未并发运动、音频或编码，也没有把配置的 30 fps 当作已达到的采集吞吐。
vendor CPP 偶发关闭告警仍需跟踪，不能据此宣称长稳和图像质量全部完成。
配置、模型路径、实测条件和运行命令见 [IMX219 采集与检测](k1-imx219.md)。

### ES8326 音频

已验证 SDK 的播音和麦克风采集同时工作。ALSA profile 将硬件侧固定为 48 kHz 双声道，
适配 SDK 请求的播放/采集格式，避免全双工时硬件采样率冲突；保留原 AIC3104 默认路径。
这不是端到端音频时延测试，也不是在新麦克风结构上完成了抚摸识别精度验证。
详情见 [ES8326 集成记录](spacemit-k1.md#es8326-audio)。

## 4. 接下来继续适配的 6 类工作

以下是后续范围和完成标准，不是已承诺的完成日期。可以独立推进的项目不互相等待，
需要实物的部分则在设备到位后开展；USB 方案不以 IMX219 完成为前置条件。

1. **运动硬件闭环（模块 3）**：确认 HAT 电源/电平/半双工接口及 K1 UART，实测 1 Mbps 下
   15 个舵机与 IMU ID 200 的收发、超时和异常处理，再验证 50 Hz 真实反馈闭环及安全行为。
2. **浏览器图传（模块 6 剩余部分）**：已有 [SDK H.264 / RTSP 预览](k1-rtsp.md)，
   后续将同一采集源的检测与叠框接入，再补齐 WebRTC 运行时并验收浏览器控制、音视频、
   延迟、异常恢复及整机并发。RTSP 子路径通过不等于完整浏览器图传通过。
3. **IMX219 / CSI / ISP（模块 5 剩余部分）**：在已接入的 MUSE-Pi-Pro / CSI3 路径上，
   配合相机团队验证曝光/白平衡、偏色/PQ、长时间稳定性和异常恢复；其他接口/模组需单独验收。
4. **ToF 外设（模块 7）**：确认实际型号和 I²C 连接，验证初始化、持续测距、数据发布及异常恢复。
5. **蓝牙与手柄（模块 9）**：确认控制器及系统服务可用，验证配对、重新连接、按键/摇杆输入和控制路径，
   包括断连时的安全处理；相关手机/网络交互还需端到端联测。
6. **RISC-V 产品化部署（模块 10 剩余部分）**：形成架构明确的构建/发布产物、板级自动安装、
   模型与运行时依赖交付、签名验证、OTA/回滚和 CI 流程；现有手动开发安装不替代这些能力。

在上述模块之外，交付前还需要**整机综合验收**：真实运动、摄像头、视觉、音频和图传同时运行时的
调度/内存占用、控制周期、温度和长时间稳定性，以及视觉标注集和具体声学结构上的精度验证。
模块单测通过不能替代这一步。

## 5. 用户现在可以做什么

当前 SDK 适合在 K1 上继续开发：原生编译和调试、运行策略与 fake IO 控制测试、验证 USB 单眼或指定 IMX219 采集，
在准备好兼容模型后运行 ORT / EP 检测、用 [RTSP 工具](k1-rtsp.md) 实时预览 IMX219，
以及使用 ES8326 录放音。当前检测与 RTSP 需分别运行，不能争用同一相机。

它**还不是插上实物即可完整行走、浏览器图传和 OTA 的成品版本**。不要在 K1 上直接执行
Radxa 专用的 `setup-board.sh`、`provision-board.sh`、`install.sh` 或安装 aarch64 发布包。
请从 [K1 开发安装指南](../robot/install-k1.md) 开始。

## 6. 与官方 SDK 的关系

我们没有删除官方 RKNN 实现或改写运动控制核心，原 Rockchip 相机、AIC3104 音频等默认后端保留；
K1 能力通过配置和可选后端接入。不过，适配也涉及 SDK 共用的配置、取帧、ORT 封装及 ALSA 设备名处理，
不是“原版源码完全不动”。例如，无效的显式媒体配置现在会报错，而不是回退到 Rockchip 默认设备，
这一行为也影响 ARM。原 RK3566 实物回归不能由 K1 测试代替。

后续更新本页时，以提交的实现和实际验收记录为依据；未接硬件、仅编译通过或只有独立 demo 的功能，
不提前标为整机适配完成。
