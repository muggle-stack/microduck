# K1 / MUSE-Pi-Pro: live IMX219 capture and ORT + EP

[English](k1-imx219.md) · [简体中文](k1-imx219_zh.md)

The new `camera.backend = "spacemit_csi"` explicitly selects the K1 CSI input.
It reuses SDK frame acquisition, image pre/postprocessing and ORT / SpaceMIT EP without changing
the Rockchip / RKNN defaults or replacing USB selected-eye capture. The headless development
tests below do not start motors, audio, encoding or WebRTC. Subsequent browser streaming and
same-source inference are covered by the [K1 WebRTC guide](k1-webrtc.md).

<a id="链路与适用硬件"></a>
## Pipeline and supported hardware

```text
IMX219 (CSI3, sensor_id=2)
  → K1 sensor / ISP / CPP (spacemitsrc, 1280×720 NV12, 30 fps)
  → videoconvert (UYVY / BT.601)→ SDK latest frame
  → existing RGB letterbox / NCHW → Rust ORT＋SpaceMIT EP
  → existing single-class duck decoder / NMS / media.detections
```

The tested board is **MUSE-Pi-Pro / K1, 8 GB, Bianbu 2.3.5, kernel 6.6.63 #2.2.9.2**.
Native GStreamer is 1.24.2; `k1x-cam` 0.2.34, `k1x-cam-lib` 0.1.8 and MPP 0.1.6~bpo2+1.
The sensor is `imx219_spm`, mode 0: 1920×1080 RAW10, 2 lanes, 30 fps.
720p is the ISP output, not a claim of a native 720p sensor mode. Other ports, images and modules
need their own validation.

The system camera stack continues to manage the ISP. No RKISP / RKAIQ calls, kernel/device-tree
changes or system camera-config replacement are involved.
`close-dmabuf=true` permits mapping for the existing CPU frame path; this is **not end-to-end zero-copy**.
GStreamer performs color conversion. CSI does not load the USB-specific MPP/OpenCV bridge;
`camera.acceleration` stays at its default `software`. That field controls the USB bridge only,
not whether the ISP uses hardware.

<a id="编译和配置"></a>
## Build and configuration

For first-time Rust and system dependency installation, see the [K1 installation guide](../robot/install-k1.md).
With an existing build cache:

```sh
cd ~/workspace/microduck
export PATH=/opt/microduck-rust-1.89.0/bin:$PATH
export CARGO_TARGET_DIR="$PWD/target"
export ORT_DYLIB_PATH=/usr/lib/libonnxruntime.so
cargo k1 --locked --bin camera-check --bin mediad -j 2
```

This updates only two binaries; another full `k1-test.sh` run is unnecessary.
Omitting `-p mediad` preserves the workspace dependency-feature set selected by the initial
`cargo k1 --bins` build, reducing rebuilds caused by feature changes.

First ensure `gst-inspect-1.0 spacemitsrc` finds the system plugin, then review:

- [camera-imx219.toml](../../deploy/k1/camera-imx219.toml): CSI, NV12, 720p30 and rotation 0.
  `detect.enabled=false` by default; inference does not start automatically.
- [imx219-csi3-720p.json](../../deploy/k1/imx219-csi3-720p.json): vendor sensor/ISP profile,
  CSI3 / sensor 2, with auto-probing, the tuning server and implicit frame saving disabled.

The TOML `camera.isp_config` and `detect.model` values are **absolute paths**.
Adjust them for a non-root user or a checkout outside `/root/workspace/microduck`.
Do not treat a different CSI connector as CSI3.
Before opening the camera, the SDK checks output dimensions, frame rate, single ISP/CPP pipeline
and online input in the JSON. A mismatch fails; it does not switch sensor or fall back to USB/Rockchip.
This backend currently accepts NV12 mono only, not SBS/ROI settings.

<a id="用户验证命令"></a>
## User verification commands

After ensuring no other process owns the camera, check capture alone:

```sh
timeout --signal=TERM --kill-after=5s 30s \
  target/riscv64gc-unknown-linux-gnu/release/camera-check \
  --config deploy/k1/camera-imx219.toml --warmup 5 --frames 120
```

Then run detection. The model must be at the example path; without it, stop after capture validation.

```sh
export ORT_DYLIB_PATH=/usr/lib/libonnxruntime.so
systemd-run --scope --quiet --collect --property=AllowedCPUs=0-2,4 \
  taskset -c 0-2,4 timeout --signal=TERM --kill-after=5s 60s \
  target/riscv64gc-unknown-linux-gnu/release/camera-check \
  --config deploy/k1/camera-imx219.toml \
  --detect --model /root/.local/share/microduck/models/duck_detect.slim.onnx \
  --warmup 5 --frames 60 --hz 2
```

The scope requires appropriate systemd permissions; the measured examples used a root shell.
`--detect --model` explicitly enables detection in the tool without editing the default-disabled config.
The hard budget is **four CPUs: 0, 1, 2 and 4**, with three EP workers on `0;1;2` and the caller on CPU 4.
`taskset` alone cannot constrain all threads of this EP; the TOML does not create a cgroup automatically.

Each frame produces a detection notification, followed by an `event=summary` record.
`inference_mean_ms` covers preprocessing, inference and NMS, not acquisition/ISP or browser latency.
`--hz 2` is the consumption rate, not a 2 fps sensor setting. A capacity-one latest-frame queue drops
old frames when the consumer is slow. Vendor camera diagnostics also write directly to stdout
and can interrupt JSON lines.

For machine-readable output, add `--report /absolute/path/to/new-report.jsonl`.
SDK events go to a new file; vendor diagnostics stay on stdout/stderr. It does not redirect
process-wide file descriptors or overwrite an existing report.

To confirm actual EP execution, add `--profile /absolute/path/to/new-profile` in a **separate short run**.
Inspect `SpaceMITExecutionProvider` nodes in the ORT trace, not just registration messages.
Profiled timings are not performance baselines.
To save a frame, use `--dump-dir /absolute/path/to/new-directory`; the directory must not exist.
It writes `mono.uyvy` and `frame.json` without overwriting previous images.

<a id="模型和精度边界"></a>
## Model and accuracy boundaries

Use floating-point opset 17 **`duck_detect.slim.onnx`**, 10,498,817 bytes, SHA256:

```text
e1e8444bc8fe9a53675f1c885b781705f8579ea17abe23bcd2b853d59c8f746f
```

Input is `images: float32[1,3,320,320]` and output `output0: float32[1,5,2100]`.
This is a compatible export of the original duck model, not generic COCO YOLO11.
It is not INT8 and does not enable FP16 epilogues.
The SDK RGB letterbox, confidence threshold 0.35 and NMS 0.5 are unchanged.
Native ORT is `/usr/lib/libonnxruntime.so` (1.24.2+spacemit.a1), SpaceMIT EP 2.0.6.
It comes from native `spacemit-onnxruntime`, not a Python wheel's dynamic library.

**Published on 2026-09-07 as the independent
[models-duck-detect-v1 prerelease](https://github.com/muggle-stack/microduck/releases/tag/models-duck-detect-v1).**
[Download the pinned model](https://github.com/muggle-stack/microduck/releases/download/models-duck-detect-v1/duck_detect.slim.onnx),
verify the SHA256 above, then point `detect.model` at its local absolute path.
Ordinary git clone does not download the model. Do not use `releases/latest`:
this model is not an SDK firmware or OTA release.

The Release also includes `SHA256SUMS`, `model-manifest.json`, `MODEL_CARD.md`, the license text,
and `duck-detect-source-v1.tar.gz` containing the original ONNX and conversion script.
The conversion was repeated before publication and produced the identical SHA256.
Both original and converted ONNX metadata retain the Ultralytics AGPL-3.0 license field;
the SDK's Apache-2.0 does not relicense the weights. Downstream users must assess the model license
for their own use. The stable board path remains
`/root/.local/share/microduck/models/duck_detect.slim.onnx`.
Historical experiments and accuracy limits are in the [model experiment](k1-duck-quantization.md).

The original opset 12 ONNX attention reshape is incompatible with this EP; renaming a file is not conversion.
EP registration/load errors fail instead of opening another CPU-only session.
Native per-node CPU fallback can still occur. Inspect a new profile for every runtime/model combination.
See the [ORT / EP integration guide](k1-duck-ort-ep.md).

<a id="2026-09-07-验证记录"></a>
## Verification record: 2026-09-07

- Mac: `cargo test --locked -p mediad -p robotd-params --lib` passed 32 + 98 tests.
  Mac tests do not validate Linux GStreamer / CSI code.
- MUSE-Pi-Pro: Rust 1.89, `cargo test --locked --release --workspace --lib
  --target riscv64gc-unknown-linux-gnu -j 2 -- --test-threads=2`:
  **719 passed, two hardware tests ignored by default**.
  This was library regression, not all binary/integration tests or another full `k1-test.sh` run.
- Explicit `camera::csi::tests::repeated_open_read_drop` passed:
  **three open/read-10-frames/close cycles in one process**, with increasing PTS each time.
  `MICRODUCK_K1_CSI_TEST_CONFIG` selects the profile; ordinary CI does not open a camera.
- Negative `camera-check` tests rejected an existing report, missing model and mono config with
  `--both-eyes` with exit 1 before starting the sensor. The existing report SHA256 was unchanged.
- An initial live EP short profile showed four `SpineSubgraph` executions assigned to
  `SpaceMITExecutionProvider` and no recorded CPU node execution.
  It overlapped compilation and profiling, so **it is not a performance result**.

Two final release-build runs follow. Neither overlapped compiler, motion, audio, encoding or WebRTC.
Both used hard cgroup `0-2,4`, the same 720p30 profile, rotation 0, floating-point model and thresholds, without profiling.

| Check | Warm-up / measurement | First run | Second run |
| --- | --- | --- | --- |
| Capture-only consumption | 5 / 120 frames | 26.72 fps | 26.74 fps |
| Live detection, mean preprocessing + inference + NMS | 5 / 60, consumed at 2 Hz | 248.94 ms | 237.55 ms |
| Live detection P95 | Same | 259.21 ms | 247.90 ms |
| PTS-span rate of frames used for detection | Same | 1.9979 Hz | 1.9980 Hz |

Both met the current 2 Hz consumption target, with no PTS reversal.
**Measured capture did not reach the configured 30 fps**; these cross-board/cross-camera numbers
are not a claimed speedup over the older K1 USB path.
All 18 sampled userspace threads were constrained by the four-CPU cgroup;
EP workers used 0, 1 and 2, caller CPU 4.
A separate final-build short profile again showed four SpaceMIT subgraph executions and no CPU node execution.
Each run produced 60 reports of 1280×720, 1,843,200-byte UYVY frames with unchanged `media.detections` format.

That scene contained no detected duck. These results establish the live data path and execution backend,
not labelled detection accuracy.
The saved ceiling/lamp image was visibly cyan-tinted with overexposed highlights.
That early result is retained for later exposure/white-balance/color regression;
the test used no additional filter and retained model precision.

Original board logs: `/root/workspace/microduck/target/imx219-sdk-check.HjPwiy/`.
Retained negative results include vendor `open /dev/ion failed!` and occasional shutdown
CPP `invalid state (1) for evt (6)` / `cam_cpp_post_buffer ... failed` messages.
The runs could finish and reopen, but that is not a zero-error or long-duration stability claim.
System vendor libraries were unchanged.

The specified MUSE-Pi-Pro / CSI3 IMX219 supports capture, browser video and same-source detection.

<a id="完成边界"></a>
## Completion boundary

Live capture and detection are integrated. The `mediad` K1 H.264 / WebRTC path also has
single-viewer video, DataChannel and same-source ORT / EP detection integration and real tests.
Browser-streaming evidence comes from the independent [WebRTC test record](k1-webrtc.md),
recorded separately from standalone `camera-check` tests.

The explicitly enabled [`camera-rtsp` tool](k1-rtsp.md) separately feeds ISP NV12 DMA-BUF into
K1 hardware encoding and RTSP/TCP for a desktop player. It does not load the detector and is not WebRTC.
Vendor ISP manages AE/AWB; the SDK does not reuse Rockchip manual exposure control.
Different-lighting exposure/PQ, quantified endurance,
abnormal recovery, labelled detection accuracy and motion/audio concurrency still need dedicated tests.
Encoding plus inference already has single-viewer WebRTC short-test evidence, not whole-robot-load acceptance.
